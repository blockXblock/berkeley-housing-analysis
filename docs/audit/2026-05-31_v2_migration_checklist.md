# v1 → v2 Migration Checklist — 2026-05-31

**Scope:** Read-only analysis. No scripts or databases modified. Maps every
publication/reporting consumer to its current source (v1 frozen
`berkeley_housing_analysis.db` vs v2 `berkeley_housing_v2.db` compat views) and
flags compat-view gaps that block migration. Internal disk only — does not touch
external drives or the running Toshiba copy.

## Root cause of stale public data (the headline)

**The live site never got flipped to v2.** `docs/explorer.html` loads
`docs/explorer_data.js`, which is generated by the **V1** script
`export_explorer_data.py` (reads frozen `berkeley_housing_analysis.db`, last
updated ~Apr 22). The v2 export (`export_explorer_data_v2.py`) writes to
`docs/explorer_data_v2_working.js` — a **staging file the live page does not
load**. The v2 pipeline was built and staged but the final cutover (point
`explorer.html` at the v2 output) was never made. Same pattern for the APR.

## Stage 4 — data delta (v2 vs v1)

- `v_projects_flat` (v2): **181** projects
- `projects` (v1 frozen): **179** projects
- Delta: **+2** projects. *Note: the count delta understates staleness — the
  live `explorer_data.js` blob itself is an old regeneration from frozen v1

## v2 compat views available (9)

`v_projects_flat`, `v_project_events`, `v_project_permits`, `v_project_affordability`,
`v_project_unit_mix`, `v_project_documents`, `v_project_geometries_current`,
`v_project_stage_spans`, `v_organizations_with_projects`.

`v_projects_flat` exposes **32 columns** in **v2 names** (`total_units`,
`filed_date`, `bp_issued_date`, `co_issued_date`, `owner_current`,
`status_code`/`status_label`) — **not** v1 names (`units`, `filed`, `bp_date`).
So repointing requires column-name remapping, and some v1 columns have **no
equivalent at all** in the view (see gaps).

## Recommended migration order

1. **PILOT — APR (`generate_apr_v2.py`).** Lowest risk, cleanest diff: output is
   tabular (Table A/A2/B CSVs), diffable row-by-row against `generate_apr.py`.
   v2 twin already reads `v_projects_flat` with no gaps. Validate, then adopt.
2. **Explorer cutover (high impact).** Validate `explorer_data_v2_working.js`
   against `explorer_data.js` (JSON diff), then point `explorer.html` at the v2
   output (or have the v2 script write `explorer_data.js`). **This is the change
   that unsticks the stale public site.**
3. **KML (`generate_kml.py`) — last.** Blocked: first extend `v_projects_flat`
   with `construction_data_reliability`, `is_uc_project`, `pipeline_stage`; then
   repoint (geometry already available via `v_project_geometries_current`); diff KML.
4. **Datasette refresh.** After the above, re-run the notebook builders (A8, D2)
   from v2 and redeploy `map.db` + `address_centric.db` to Fly.

### Semantic caveat for diff-verification
v2 uses **`MIN(event_date)`** for some timeline anchors where v1 may have used
**`MAX`**. When diffing a repointed script's output, **expect some intentional
date differences** — not a clean zero-diff. Characterize each diff as
intentional (anchor change) vs regression before adopting.
