# Completion display derives from the verdict (co_date), not the stage field

**Date:** 2026-06-15 · **Principle:** ADR-001 (one definition, derived from the canonical source) applied to the explorer's "Completed" display.

## Problem
Two materializations of "completed" had drifted: the verdict layer (`v_projects_flat.co_issued_date`, **674** raw / **672** stub-rejected) and the materialized `projects.current_stage_type_id='completed'` (**744**). The explorer published the stage count (744 green map markers) alongside a co_date CO stat — a public self-contradiction, two data-driven completion numbers disagreeing on the same page.

## Decision (Option A — derive, don't sync)
Do **not** maintain two materializations and sync them (that perpetuates drift). Derive the completion display **once, from the canonical source**:
- **`validate_co_date`** (export) now rejects only the `2024-01-01` migration **stub** (2 placeholder projects, proj137/138), keeping all real dates regardless of year. The prior `year < 2020` cutoff wrongly dropped **145 genuine 2018-2019 completions** — our APR spans 2018-2025, so they must show. Result: **672**.
- **Export status** (`export_explorer_data_v2.py`): `status='Completed'` **iff** a valid `co_date` is present. A stale `stage='completed'` without a valid CO date falls back to its milestone-derived status (Under Construction if it has permits, else Entitled / Under Review / Pre-Application) — **never fabricated as Completed**. So the map markers (672) cannot diverge from the CO stat (672).
- `current_stage_type_id` **stops driving the published completion display**; it remains for internal use. A clean re-derivation of the stage field from milestones is a separate later task (the 74 stale-completed projects lack cleanly-derivable stages — 53 would wrongly become pre-application from patchy milestone data, so we did NOT overwrite them).

## Genuine data-error fix (DB write)
proj164 (1752 Shattuck, **72-unit**, inspection-confirmed CO 2026-05-26) and proj154 (2001 Ashby, CO 2025-06-01) carried `stage='withdrawn'` despite verified completions — exactly why stage must not drive the display. Corrected `withdrawn → completed` (snapshot `keep_snapshot_2026-06-15_pre-stage-fix.db`, evidence untouched).

## Consumer coherence (one definition)
- Explorer CO stat == map markers == **672** (same source, can't diverge).
- `generate_apr_v2.py` now applies the same `2024-01-01` stub-rejection (APR 2024: 88 → **86**, matching the view). Per-year CO: 2023=103, 2024=86, 2025=94.
- The non-v2 `export_explorer_data.py` (read raw events, bypassed the fix; false "ONLY script" header) is **sequestered** to `scripts/superseded/` so it can't silently revert the published verdict layer.

## Served-file switch
This republish is the **first time the verdict layer reaches the live site**: `docs/explorer_data.js` is now generated by the view-driven `export_explorer_data_v2.py` (was the raw-events non-v2 export).
