# Discovery: project_events pollution from v1->v2 migration

**Date:** 2026-05-16 (session 16:00-end)
**Branch:** dev
**Status:** Discovery complete. Remediation deferred. No code changes made tonight beyond classifier work that is now identified as solving the wrong problem at the wrong layer.

## What was being investigated

Starting goal: fix the Berkeley Housing Pipeline Explorer at berkeleybuild.com, which displayed 38 projects as "Completed" in 2025, of which a 10-project audit found 50% were misclassified. The handoff prompt from the prior session attributed this to a "Fix A" script that advanced any project to Completed if it had any CO event, regardless of whether the CO was on the primary development permit or a subsidiary trade permit (solar, electrical, demolition, retrofit).

The session began by building a description-text classifier (`scripts/permit_role_classifier.py`) intended to distinguish primary new-construction permits from subsidiary trade permits. Several hours into the work, an inspection of the v2 schema revealed valuation as a strong structured signal. An Accela sidebar query on a single permit (B2024-01268, 2016 Ashby Ave) then revealed that local DB records for the project differed materially from the authoritative Accela record. Following that thread led to inspecting the events on that project, where the actual bug was found.

## The actual bug

The pollution lives upstream of the classifier and upstream of the view that derives project stage. It is in `scripts/migration/migrate_v1_to_v2.py`, the script that generated the v2 `project_events` table from v1 source data on April 27, 2026.

Three concurrent sources of pollution:

**Source 1 - Status-action mapping (lines 241-261).** A lookup dictionary maps Accela workflow status strings to v2 event type codes. Two mappings are semantically wrong:
'approved': 'entitlement_approved',
'approved w/conditions': 'entitlement_approved',
'approved/case closed': 'entitlement_approved',
'approved bemp': 'entitlement_approved',
'auto-closed': 'project_withdrawn',

Accela's "Approved" or "Approved w/Conditions" status fires *per division review* - Building, Zoning, Fire, Public Works, Environmental Health, Traffic, PSC - each emitting its own approval event when that division's review completes for that resubmittal cycle. The migration script translates every such occurrence into one `entitlement_approved` event. But `entitlement_approved` is defined in `vocabulary_event_types` as implying `stage = entitled (3)`, meaning the project crossed the entitlement threshold - a single milestone, not a per-division status.

Accela's "Auto-Closed" is a routine workflow status (timeouts, applicant-pause, administrative closure for non-terminal reasons). The migration script maps it to `project_withdrawn`, which implies `stage = withdrawn (8)`. This produces false withdrawal events on projects that were never withdrawn.

**Source 2 - Date column events (lines 802-822).** A second event-generation path reads v1's project table and emits one event per non-null date column (`filed`, `entitled`, `bp_issued`, `co_date`, etc.). This is sensible in isolation but additive with Source 1: a project gets entitlement events from both pathways with no deduplication.

**Source 3 - Synthetic entitlement events (lines 1165-1232).** When `project_versions.effective_date` exists but no source event was found, a synthetic `entitlement_approved` event is created and flagged `is_inferred=1, confidence=medium`. The audit flag is captured but the event still fires the implies_stage logic in the view. Three pathways feed the same event type; none coordinates with the others.

## Scope of pollution (as of 2026-05-16)

From queries against the current v2 database:

- 7 projects have multiple `project_withdrawn` events. The worst: project 164 (1752 Shattuck) with 16, project 143 (2902 Adeline) with 14, project 144 (2127 Dwight) with 12, project 157 (2587 Telegraph) with 11.
- 30+ projects have duplicate `entitlement_approved` events. The worst: project 157 (31 events), project 164 (28), project 144 (26), project 143 (23). Total `entitlement_approved` events in the database: 283. A conservative read suggests roughly half are duplicates.
- 8 projects are currently tagged with `current_stage_type_id = 8 (withdrawn)`. At least one of those, project 141 (2016 Ashby), is verifiably not withdrawn: Accela shows it issued, $38.5M valuation, $2.19M in fees paid, foundation inspections in progress April-May 2026.
- 64 total `project_withdrawn` events exist in the database; the vast majority appear on projects that were never withdrawn.
- 927 `status_update` events - far above any other event type - were also generated by the same migration. These don't drive stage but inflate the events table.

The pollution scales with the number of resubmittal cycles a project had in Accela. High-profile, complex projects with multi-year reviews accumulated the most spurious events. Small projects with simple review histories are less affected.

## What this means for the published Citizen APR

**The published 12.4% RHNA progress figure on building permits, the 169-project corpus, and the 11,235-unit total should be considered preliminary pending re-derivation from cleaned event data.**

The migration that produced the polluted events ran April 27, 2026. The Citizen APR was generated and distributed after that date. The APR pipeline consumes `project_events` either directly (event counts) or via `v_project_stage_spans` (the view that aggregates events into stages). Either way, the upstream pollution propagates.

The specific quantities most likely affected:

- **Entitled-stage unit counts.** Each duplicate `entitlement_approved` event has an event_date. If the APR or any derived dashboard counts entitled-stage events per year, projects appear in multiple years simultaneously.
- **Stage-transition timing.** Projects whose first spurious `entitlement_approved` event predates their real entitlement may show as entitled earlier than they actually were, biasing year-over-year comparisons.
- **The entitled-to-construction gap.** The handoff mentioned "a significant entitlement-to-construction gap" as a Citizen APR finding. If the entitled-stage population is inflated by duplicates, the gap is overstated.
- **The withdrawn count and any "stalled project" figure.** The 8 projects currently tagged withdrawn include false withdrawals. Real withdrawals are a subset; the figure shown is an upper bound on the real one.

The completed-stage count (the 38 false completions that started this work) is a separate but related issue: the classifier work this session was intended to address it, but the underlying mechanism - CO events firing on subsidiary permits - also stems from migration logic, not just classifier logic.

**An audit-then-revise process is the appropriate response.** Re-deriving the APR from cleaned events, side-by-side with the published version, will quantify whether the corrections are material or noise. Recipients of the Citizen APR (Terner Center, Possibility Lab, City staff, City Council) should be informed of the data quality finding once the magnitude of revision is known.

## What was built this session that is salvageable

- `scripts/permit_role_classifier.py` (the description-text classifier) and its baseline audit work in `analysis/audit_2026-05-16/`. The classifier solves the wrong problem at the wrong layer, but it does encode useful pattern knowledge for cases where local data is genuinely insufficient. It can become a residual fallback in a tier-3 position rather than the primary stage-derivation mechanism.
- The Accela snapshot workflow validated on B2024-01268. One scrape captured Job Value, full Project Description, Processing Status with timestamps, Related Records (parent permit ESR-2024-00678), and fee history. This is the authoritative-data tier that should replace migration-derived events as the source of truth.
- The valuation finding ($500K threshold cleanly separates completes from non-completes in the 55-CO-event subset, with caveats about NULL valuations and single-ADU edge cases). This becomes a tiebreaker in the future classification architecture, not the primary signal.

## What needs to happen, in order

1. **v1 source data audit.** Open the v1 database file and check, for the 30+ projects with duplicate entitlement events: what did v1 actually have? Was the `projects.entitled` date column correct on its own? Did v1 have a per-status-action history that the migration script flattened incorrectly? This determines whether the fix is in the migration mapping or in the source data interpretation.
2. **Methodology note revision for public.** Once the v1 audit is done and the magnitude of revision is known, revise this note into a public-facing methodology page. Notify Citizen APR recipients.
3. **Cleanup script design.** Either re-run the migration with corrected mappings (losing any manual corrections made since April 27), or write a targeted cleanup that removes spurious events from existing data. Decision depends on what the v1 audit reveals.
4. **Accela snapshot architecture.** Design `permit_accela_snapshots` schema based on the B2024-01268 capture. Identify the population of permits that need Accela refresh (NULL valuation, `source_system = v1_events_reconstruction`, `permit_status_type_id = 12 (unknown)` - ~100+ permits). Plan a batched sidebar-scrape workflow.
5. **Stage derivation redesign.** Once events are cleaned and Accela snapshots are populated, the `v_project_stage_spans` view can be revised to (a) use a permit_role join condition for `co_issued` events, and (b) read from Accela snapshots when present. The description-text classifier becomes a residual fallback.
6. **APR re-derivation and revision.** Run the APR pipeline against the cleaned data. Compare to the published version. Issue a revised Citizen APR with a methodology revision explaining the data quality finding.
