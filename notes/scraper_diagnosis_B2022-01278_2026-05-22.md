## 6. Diagnostic hypothesis

**Hypothesis (c) — Scraper found the page but the parser failed to match it because the page is a different DOM type (CapDetail vs results list).** Specifically:

- The scraper visited `CapHome.aspx?module=Building`, filled the permit-number input with `B2022-01278`, and clicked search. This is correct.
- Accela's search behavior **branches on result cardinality**:
  - **Multiple records match** (e.g., a permit with REV/DEF sub-records, or a multi-parcel permit emitting multiple rows) → renders the search-results list page with one `<a href=".../CapDetail.aspx?...">` anchor per row.
  - **Exactly one record matches** → auto-navigates to that record's CapDetail page directly.
- `url_discovery_scraper.py::_parse_result_rows` assumes the post-search page is always the results-list form, and parses by selecting `a[href*='CapDetail.aspx']` anchors. On the CapDetail page (the single-result case) those anchors don't exist, so `records_seen=0` → `not_found`.
- The capID triplet for B2022-01278 IS present on the captured HTML — in the form action attribute, in inline JavaScript URLs, and in inspection-detail href patterns — but never inside an anchor matching the current selector.

**This hypothesis cleanly explains Part 4's headline finding** that all 59 not_found permits in the resume run have `cpra_row_count = 1` (single-parcel), while all 25 multi-parcel permits (cpra_row_count ≥ 2) succeeded. Multi-parcel permits tend to have multiple matching records in Accela (master + REVs/DEFs + multiple parcel rows), tripping the multi-result branch and rendering the parseable results-list page. Single-parcel small-work permits tend to have exactly one matching record, tripping the auto-navigate-to-CapDetail branch.
